# 📐 Memory protocol — как работает мозг

Этот vault (`brain`) — **канонический мозг**. Один источник правды, два потребителя: я (Claude Code) и.

## Слои — контракт задан в [[brain-architecture]]

С 02.08.2026 уровней **четыре**, и у каждого жёсткий лимит, который проверяет
<локальный файл>. Раньше лимитов не было, и L0 вырос до 49 КБ, то есть ~12 300
токенов в каждой сессии вместо экономии.

- **L0 — **: маршрутизатор. 132 строки, 8 КБ, ≤200 символов на строку.
- **L1 — карта домена** (`_System`, `_UTD`, `_Jarvis`, индекс проекта): до 400 строк.
- **L2 — атомарная заметка**: один факт или тема, до 500 строк.
- **L3 — поток** (журналы, уроки, предложения): без лимита, но **целиком не читается никогда**,
 только верх или `grep`.

Полный контракт, четыре рода содержимого и правило добавления информации — [[brain-architecture]].

## Формат заметки (frontmatter обязателен)
```markdown
---
name: <kebab-slug> # = имя файла без.md, цель для `ссылок`
description: <одна строка> # по ней решаю релевантность, не открывая файл
type: reference | project | brand | tool | index | moc
updated: YYYY-MM-DD
---

<суть. Связи — через `другая-заметка`. Линкую щедро.>
```

## Чтение (как я экономлю токены)
1. Сессия стартует → читаю **только **.
2. Задача совпала со строкой индекса → открываю MOC домена → нужную L2-заметку.
3. Нет совпадения → ничего не гружу.

## Запись (как мозг растёт)
1. Узнал что-то долгоживущее → проверяю, нет ли уже заметки (Grep по `name:`/`description:`).
2. Есть → **обновляю** её (не плодим дубликаты). Нет → создаю L2-файл по формату.
3. Добавляю строку в нужный MOC (карту домена). **В — только если появился новый домен или новое железное правило**: лимит L0 8 КБ проверяет `brain-doctor.sh` ([[brain-architecture]]).
4. `updated:` ставлю текущей датой.

## Что сюда писать
- Бренд, голос, пайплайн, состояния проектов, указатели на креды (**не сами секреты**), выученные правила/фидбек, тех-решения, которые не выводятся из кода.

## Что НЕ писать
- Секреты/токены (только указатель на защищённый файл, см. ).
- То, что и так в коде/гите.
- Эфемерное «только для этого разговора».

## 📇 ПРОТОКОЛ ЗАХВАТА ФАКТОВ (домен )

Цель — никогда не путать «чей email / чей контакт / какой аккаунт наш». Работает как рефлекс, а не по запросу.

**Триггеры — записать СРАЗУ, в том же ходе, где факт прозвучал:**
- человек ПРЕДСТАВИЛСЯ («меня зовут X», «я твой оператор») → секция в; операторов несколько, факты одного не приписывать другому
- оператор назвал СВОЙ идентификатор (email, телефон, ник, аккаунт) → в его секцию (+ перекрёстно в )
- прозвучал человек с повторяющейся ролью (сотрудник, партнёр, подрядчик, получатель) → строка в
- новый аккаунт/домен/ID системы бренда → строка в
- новый файл с кредами → УКАЗАТЕЛЬ (путь) в, сами секреты — никогда
- правило/вкус/ошибка → это НЕ Facts: Preferences / (как в петле ниже)

**Формат факта:** идентификатор — роль — принадлежность (владельца / команды / бренда / внешний) — дата и источник. Не уверен в принадлежности → ставлю ❓ и уточняю одним вопросом при удобном случае, но факт записываю сразу.

**Гигиена:** один субъект = одна строка (крупный новый субъект, напр. новый бренд — новая нода); конфликт с записанным → обновить строку, старое значение пометить «устарело: было X», не хранить два «истинных» варианта; перед записью Grep по Facts/ — не плодить дубликаты.

**Что НЕ захватывать:** одноразовые адреса из парсеров/рассылок (живут в своих таблицах); секреты/токены; то, что уже в коде/гите; эфемерное «только для этого разговора».

## 🔄 ОПЕРАЦИОННАЯ ПЕТЛЯ (обязательна — это и есть «учусь и меньше ошибаюсь»)

Любая рабочая задача проходит 3 такта:

**1. ПЕРЕД работой — собрать контекст из мозга (дёшево, по индексу):**
- Открыть нужный **Playbook** (`Playbooks/*`) — как мы делаем этот тип задач правильно.
- Открыть нужные **Preferences** (`Preferences/*`) — что владелец любит/не любит в этом домене.
- Глянуть **** — какие ошибки уже разобраны, чтобы не повторить.

**2. ВО ВРЕМЯ — вести по playbook**, через его гейты согласования. Не перепрыгивать этапы.

**3. ПОСЛЕ — зафиксировать обратную связь (КРИТИЧНО):**
- владелец поправил / похвалил / сказал «вот так правильно / так нет» → **немедленно**:
 - правка/вкус → дописать в нужный `Preferences/*`;
 - ошибка, которую нельзя повторять → новая запись в **** (формат: что пошло не так → правило теперь);
 - удачный приём → закрепить в playbook или.
- Быстрый скан разговора: прозвучали ли новые идентификаторы/контакты/аккаунты → захватить по протоколу фактов (выше).
- Обновить `updated:` и строку в индексе.

> Без такта 3 система не учится. Любой сигнал «нравится/не нравится/правильно/неправильно» = триггер записи. Это важнее, чем закончить быстро.

## 🧹 Гигиена свежести (добавлено 2026-07-26)
Устаревание не должно быть молчаливым, поэтому действует правило: заметка с `updated:` старше **30 дней** = кандидат на ревью при первом же заходе в её домен — прочитать, сверить с реальностью и либо подтвердить актуальность (bump `updated:`), либо обновить содержимое, либо пометить как историческую.
- Инструмент: <локальный файл> (топ старых заметок; `--all`, `--days N`). Запускать при старте крупной задачи в домене и при любом «мозг что-то говорит не то».
- Ревью канон-заметок (System/Playbooks/Preferences) — изменения содержимого через ветку proposals на апрув владельца, как и всё остальное; bump даты после подтверждения актуальности — можно сразу.
- Прецедент, зачем это нужно: `security-model` описывала «age не установлен, FileVault выключен», хотя реально всё давно стояло — заметка была на месяц старее действительности (исправлено 2026-07-26).
